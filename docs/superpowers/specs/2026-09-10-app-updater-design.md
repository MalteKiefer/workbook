# In-App Updater Design

## Goal

Add a "Aktualisierung" (Update) section to Settings where the user can see
the currently installed version, check whether a newer release exists on
GitHub, and install it without leaving the app — applied on the next
restart, which the update flow itself triggers.

## Motivation

The app already ships versioned releases to GitHub (`v0.1.0` through
`v0.3.0` so far, built for Windows/Linux/macOS by `.github/workflows/release.yml`).
There is currently no way to learn about a new release except checking
GitHub by hand, and no way to install one except re-downloading the
installer manually.

## Architecture

Tauri's own first-party updater plugin (`tauri-plugin-updater` +
`@tauri-apps/plugin-updater`), pointed at the same GitHub Releases this
project already publishes to. This is the standard, maintained path for a
Tauri app and needs no separate update-hosting infrastructure — it works
off Tauri's own build of an installer manifest (`latest.json`), which
`tauri-apps/tauri-action` (already used in `release.yml`) generates and
uploads automatically as a release asset once signing is configured.

**Verified against the current Tauri v2 docs and the `tauri-action` source
before writing this spec** (not assumed):

- `tauri.conf.json` gets a new `plugins.updater` block: `endpoints`
  (a single URL, `.../releases/latest/download/latest.json`) and `pubkey`
  (the public half of a signing keypair, embedded directly as its
  base64 content — not a file path). `bundle.createUpdaterArtifacts: true`
  is required alongside it.
- The keypair is generated once via `npx tauri signer generate`. The
  private key and its password are never committed — they live only as
  two GitHub Actions repository secrets, `TAURI_SIGNING_PRIVATE_KEY` and
  `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, which `tauri-apps/tauri-action`
  reads automatically when present (no extra `with:` input needed beyond
  what `release.yml` already has) and uses to sign every build artifact
  and to build/sign `latest.json` itself.
  **Already done as of this spec being written**: the keypair was
  generated, both secrets were set on the `MalteKiefer/workbook` GitHub
  repo, and the private key/password were deleted from local disk —
  the plan's first task only needs to add the public key's content to
  `tauri.conf.json`.
- `tauri-action`'s `uploadUpdaterJson` input defaults to `true` — no
  workflow change needed there beyond the signing env vars already being
  available as secrets.
- The three-OS matrix in `release.yml` (`ubuntu-latest`, `windows-latest`,
  `macos-latest`) already correctly accumulates every platform's installer
  assets into one shared (non-draft) GitHub Release — confirmed by the
  real `v0.2.0`/`v0.2.1`/`v0.3.0` releases this project has already
  published, each showing `.msi`/`.exe`/`.deb`/`.rpm`/`.AppImage`/`.dmg`
  side by side from 3 separate CI jobs. `tauri-action`'s own changelog
  documents explicit handling for re-running/multi-job updater-JSON
  generation against the same release, so `latest.json` is expected to
  accumulate the same way. This plan's Task 2 includes downloading the
  real, post-release `latest.json` and confirming by inspection that it
  lists all 3 platforms — treated as something to verify against evidence
  once real CI output exists, not assumed correct from documentation
  alone.
- Platform target keys inside `latest.json` (e.g. `darwin-aarch64` for
  Apple Silicon) are generated by `tauri-action`/`tauri-plugin-updater`
  internally and read back by the same plugin client-side — this
  implementation never needs to know or hardcode them.
- **Linux limitation (accepted, not solved here, matches upstream Tauri
  constraints):** the built-in updater only knows how to replace an
  AppImage. A user who installed via `.deb`/`.rpm` continues to update via
  `apt`/`dnf` as before — `check()` simply won't offer an install path for
  those, which the UI surfaces as "kein Update über diese
  Installationsart verfügbar" rather than a silent no-op or a crash.

## Frontend

New Settings tab "Aktualisierung", added the same way the "Tastaturbelegung"
tab was (extend `SettingsTab` in `src/state/appStore.ts`, a new
`TabButton`/conditional render in `SettingsView.tsx`).

New `src/components/UpdateSettingsView.tsx`:

- On mount, reads the running app's version via `getVersion()`
  (`@tauri-apps/api/app`) and displays it.
- "Nach Updates suchen" button calls `check()` from
  `@tauri-apps/plugin-updater`. Three outcomes: no update (`check()`
  resolves `null`) shown as "Aktuell — keine Updates verfügbar"; an update
  object resolves, shown as "Version `X.Y.Z` verfügbar" plus its release
  notes (`update.body`, the GitHub Release's own description text — this
  app already writes a plain description via the tag message, no new
  authoring step needed) and an "Installieren und neu starten" button;
  the check itself throws (network failure, no updater artifact for this
  platform/install type), shown as a plain error message, not a crash.
- "Installieren und neu starten" calls `update.downloadAndInstall()` with
  a progress callback (shown as a simple percentage, computed from the
  `Started`/`Progress`/`Finished` event payloads the callback receives),
  then `relaunch()` from `@tauri-apps/plugin-process`. No confirmation
  dialog beyond the button's own label already stating what it does —
  this mirrors how "Speichern" elsewhere in Settings acts immediately on
  click, and the whole point of this button is the restart, not a
  reversible action needing a second confirm.
- No auto-check-on-startup and no background polling in this pass — purely
  user-initiated, reachable only by opening this Settings tab. (A
  startup check is a reasonable follow-up; out of scope here, matching
  YAGNI — nothing asked for it and it adds a "silent background network
  call" surface this offline-first app doesn't currently have anywhere
  else.)

## Backend

No new Tauri commands. `tauri-plugin-updater`'s and
`tauri-plugin-process`'s own commands (registered by their `Builder::new().build()`/
`init()` calls in `lib.rs`, same pattern as every other plugin already
there) are called directly from the frontend via the plugin's JS bindings
— this project's existing plugins (dialog, opener, autostart) already work
this way, no app-specific Rust wrapper needed.

Two new Cargo dependencies (`tauri-plugin-updater`, `tauri-plugin-process`),
two new npm dependencies (`@tauri-apps/plugin-updater`,
`@tauri-apps/plugin-process`), and two new capability entries in
`src-tauri/capabilities/default.json` (`updater:default`,
`process:allow-restart`) — `process:allow-exit` is not needed, this app
never calls `exit()`, only `relaunch()`.

## Explicitly not doing

- No update channel selection (beta/stable) — this project ships from one
  branch with one release cadence, matching how tags are cut today.
- No delta/differential updates — Tauri's updater always ships a full
  new installer; not something this app's config controls.
- No startup auto-check or background polling (see Frontend section).
- No changes to how releases are authored (tag message, release notes) —
  the existing `git tag -a v... -m "..."` workflow already produces a
  release body the updater's `update.body` can display as-is.
