## Concerns / crate API notes

One real mismatch between the brief and the actual crates.io setup, worth
flagging explicitly:

- **The brief's `Cargo.toml` snippet does not resolve as written.**
  `s3 = { version = "0.37.2", default-features = false, features = ["sync-rustls-tls"] }`
  fails with "candidate versions found which didn't match: 0.1.36, 0.1.34,
  0.1.30, ...", because crates.io already has a separate, unrelated
  package that was abandoned long ago and is literally named `s3` (top
  version 0.1.36), with nothing to do with `rust-s3`. The brief's own
  prose correctly says
  "crates.io package name `rust-s3`, library/import name `s3`", but the
  `Cargo.toml` snippet it then gives omits the Cargo dependency rename
  syntax needed to actually get that package under the `s3` import name.
  The fix, which this implementation used, is:
  ```toml
  s3 = { package = "rust-s3", version = "0.37.2", default-features = false, features = ["sync-rustls-tls"] }
  ```
  Everything else about the dependency (the feature name, the
  `default-features = false` requirement, no new tokio dependency) was
  correct once resolved this way; confirmed with `cargo tree -p rust-s3 -e normal`
  that `sync-rustls-tls` pulls in `attohttpc`/`rustls` and no `tokio`
  anywhere in that subtree.

Everything else in the brief was verified directly against the downloaded
source of the exact resolved versions (`rust-s3` 0.37.2, `aws-creds`
0.39.1, `aws-region` 0.28.1) and matched exactly, with no adaptation
needed:

- `Bucket::new(name: &str, region: Region, credentials: Credentials) -> Result<Box<Bucket>, S3Error>`
  matches the brief exactly (`src/bucket.rs`).
- `Credentials::new(access_key: Option<&str>, secret_key: Option<&str>, security_token: Option<&str>, session_token: Option<&str>, profile: Option<&str>) -> Result<Credentials, CredentialsError>`
  matches the brief exactly (`aws-creds/src/credentials.rs`).
- `Region::Custom { region: String, endpoint: String }` matches the brief
  exactly (`aws-region/src/region.rs`).
- `bucket.put_object(path, content)` and `bucket.list(prefix, delimiter)`
  both exist as plain, unsuffixed sync method names once the `sync`
  feature is active (enabled transitively by `sync-rustls-tls`), exactly
  as the brief claimed. This was worth double checking directly: the
  crate's source also defines separate `_blocking` suffixed methods (for
  example `put_object_blocking`), but those are gated by a different,
  unused `blocking` feature that layers a blocking wrapper over an async
  tokio/async-std runtime, not by `sync`. The plain names are correct for
  this feature set, confirmed by reading the `#[maybe_async::maybe_async]`
  attribute and the feature table in `rust-s3`'s own `Cargo.toml`.
- `ResponseData::status_code(&self) -> u16` matches, so the brief's
  `(200..300).contains(&response.status_code())` check compiles and works
  as written.
- `S3Error` derives `thiserror::Error` with a `#[error("...")]` message on
  every variant, so `format!("...: {e}")` works exactly as the brief
  assumed; no `.to_string()` workaround was needed.

No other adaptation was necessary anywhere in Tasks 2 through 6; the
brief's Rust and TypeScript snippets were used essentially verbatim aside
from the `Cargo.toml` package rename fix above and `cargo fmt`'s routine
line wrapping.
