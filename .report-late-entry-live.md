# Report: "Nachträglich erfasst"-Hinweis live im Journal (late-entry-live)

## Summary

`Config::late_entry_threshold_hours` (default 24) previously only ever flagged a late
entry inside the PDF export path (`commands::export::to_pdf_entry`). An admin backdating
an entry got no feedback anywhere else in the app. This adds one new read-only Tauri
command exposing that threshold to the frontend, a small pure TypeScript helper that
mirrors the PDF path's exact late-entry check, and a live badge/note in both the Journal
list (`JournalView.tsx`) and the entry detail view (`EntryDetailModal.tsx`). No changes
to the `Entry` DTO, `list_entries`, or `get_entry`: everything needed
(`performed_at_utc`, `created_at_utc`, `created_at_tz`) was already present on the
frontend's existing `Entry` shape.

## Files created / modified

Backend (Rust):
- `src-tauri/src/commands/settings.rs`: added `get_late_entry_threshold_hours`, a
  sync, `Result`-free read of `Config::late_entry_threshold_hours` from the app state's
  config mutex, placed at the end of the file (after `set_theme_preference`) to keep the
  existing `get_theme_preference`/`set_theme_preference` pair together.
- `src-tauri/src/lib.rs`: registered `commands::settings::get_late_entry_threshold_hours`
  in the `invoke_handler!` list, directly after `commands::settings::set_theme_preference`.

Frontend (React/TypeScript):
- `src/lib/lateEntry.ts` (new): `isLateEntry(performedAtUtc, createdAtUtc, thresholdHours)`,
  a pure function mirroring `to_pdf_entry`'s check exactly (same `Math.abs()`, same
  hours unit, same strict `>`), plus `useLateEntryThreshold()`, a tiny shared hook that
  fetches the threshold once on mount via `get_late_entry_threshold_hours` so neither
  component below duplicates that `invoke()` call.
- `src/components/JournalView.tsx`: calls `useLateEntryThreshold()`; added a
  `lateCreatedAtDisplays` map populated (only for entries that are actually late, to
  avoid invoking `format_timestamp_for_display` for every on-time entry) via the same
  `Promise.all` batching pattern already used for the row's `performed_at` timestamp
  column; renders a small `"Nachträglich"` pill next to the category label (same visual
  language as `TagChip.tsx`'s pill, in `var(--text-muted)`, no colored dot, since this is
  informational, unlike the maintenance-overdue red dot in `SystemListView.tsx`), with a
  `title` tooltip reading `Nachträglich erfasst: {created_at formatted}`, matching the
  PDF export's own note wording exactly.
- `src/components/EntryDetailModal.tsx`: calls `useLateEntryThreshold()`; the existing
  entry-load effect now also fetches a `created_at` display string alongside the existing
  `performed_at` one (one extra `format_timestamp_for_display` call, folded into the
  same `Promise.all`); renders a `"Nachträglich erfasst: {created at formatted}"` note
  directly under the title/timestamp header, shown only when the entry is late.

No settings UI was added or changed, and no `set_late_entry_threshold_hours` command was
added; this is explicitly out of scope per the brief (see the deviations section below for
a follow-up suggestion).

## Deviations from the brief (with reasoning)

- **No unit test file added for `isLateEntry`.** Per the brief's own instruction, I
  checked first: there is no `*.test.ts`/`*.spec.ts` file anywhere in this frontend, no
  `src/lib/*.ts` testing convention, and no test runner (vitest/jest/etc.) configured in
  `package.json`. Per the brief's explicit fallback ("don't invent a new test harness this
  codebase doesn't already have"), I did a careful manual line-by-line comparison against
  `to_pdf_entry` instead (documented above) rather than introducing a new test tool.
- **Judgment call: `useLateEntryThreshold()` shared hook, used in both components.** The
  brief offered this as an explicit either/or ("your call, either is fine"). I used the
  shared hook in *both* `JournalView.tsx` and `EntryDetailModal.tsx` (not just
  `EntryDetailModal.tsx`, where the brief's text technically raised the option) since it's
  a strict improvement in both places: it removes the duplicate
  `useState`/`useEffect`/`invoke` boilerplate the brief's own inline snippet would have
  otherwise introduced twice.
- **Judgment call: batch-fetch `created_at` display only for late entries in
  `JournalView.tsx`, not for every row.** The brief didn't specify whether the
  `created_at` formatting for the badge's tooltip should be fetched for all rows or just
  late ones. Since the formatted string is only ever consumed by the late badge's `title`
  attribute, I filter to just the entries that are actually late before invoking
  `format_timestamp_for_display`, so a Journal page full of on-time entries doesn't
  trigger dozens of pointless extra backend calls. This mirrors the existing codebase's
  general economy (e.g. `SystemListView.tsx`'s overdue-since formatting only runs for
  overdue rows).
- **Discovered pre-existing inconsistency between the two export paths (not fixed, out of
  scope).** `commands::export::to_pdf_entry` (PDF) computes lateness as
  `(created - performed).num_hours().abs() > threshold_hours`, while
  `export::markdown::late_entry_note` (Markdown/manual export) computes it as
  `(created - performed).num_hours() >= threshold_hours`, with no `.abs()`. These two
  already-shipped code paths can disagree at the margins (e.g. a negative gap from clock
  skew, or a gap exactly equal to the threshold). The brief explicitly named the PDF path
  as the one to mirror and called out both the `.abs()` and the strict `>`, so
  `isLateEntry` intentionally matches `to_pdf_entry`, not the Markdown path. Flagging this
  as a possible follow-up: reconciling the two export paths to agree with each other (and
  with this new live check) would remove a subtle "PDF says on-time, Markdown export says
  late" discrepancy for an entry landing exactly on the threshold.
- **Possible follow-up (per the brief's own prompt): a Settings UI control.** As directed,
  I did not build one. If a settings control for `late_entry_threshold_hours` would be
  valuable, worth doing later: right now the value is only reachable by hand-editing
  `config.toml`, which is a rough experience for the target single-admin user contrasted
  with `theme_preference`'s already-wired settings toggle.
