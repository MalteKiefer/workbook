## Concerns

- **Bug found and fixed in the brief's own test code**: the `seed_entry` helper in Task 2's `db/entry_revisions.rs` test module hardcoded `short_code: "ACME".to_string()` for every call. `customers.short_code` is `UNIQUE` (`migrations/0001_init.sql`), so `list_for_entry_excludes_other_entries` — which calls `seed_entry` twice to get two separate entries — failed with `Database("UNIQUE constraint failed: customers.short_code")`. Fixed by giving `seed_entry` a `short_code: &str` parameter, with callers passing `"ACME"` (single-customer tests) or `"ACME-A"` / `"ACME-B"` (the two-customer test). No other test logic changed.
- **`color-mix()` for the diff backgrounds**: used `color-mix(in srgb, var(--danger) 15%, transparent)` / `color-mix(in srgb, var(--success) 15%, transparent)` per the brief's suggested pattern, since no existing `color-mix` precedent exists elsewhere in `src/`. This relies on the WebView2/Chromium engine Tauri uses on Windows supporting `color-mix()` (it does, from Chromium 111+); flagging in case the app's minimum supported WebView2 runtime is older than that.
- **Per-revision timestamp formatting**: Task 6 says to format each revision's timestamp "the same way the rest of this file already formats other timestamps," which in `EntryDetailModal.tsx` means calling the `format_timestamp_for_display` Tauri command via `invoke` (unlike `AuditLogPanel.tsx`, which uses `new Date(...).toLocaleString("de-DE")` directly). I followed `EntryDetailModal.tsx`'s own convention as instructed, fetching all revision display strings in parallel via `Promise.all` alongside the revisions fetch. This means one extra `invoke` round-trip per revision when the modal opens; fine for the expected revision-list sizes here, but worth knowing if an entry ever accumulates very many revisions.
