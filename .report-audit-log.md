## Deviations from the brief (with reasoning)

1. **`list_for_entity`'s `ORDER BY` gained a tiebreak on `id DESC`.** The brief's exact SQL was `ORDER BY at_utc DESC`. Writing the brief's own required "ordering test (three records, newest listed first)" surfaced a genuine bug: `at_utc` only has millisecond resolution, and three `record()` calls in a tight loop (the test itself, but just as plausibly a CSV import loop in production) can land in the same millisecond. SQLite then leaves the relative order of tied rows unspecified, and the test failed on its first run (`left: "erster Eintrag", right: "dritter Eintrag"`) because ties came back in ascending insertion order, not newest-first. I changed the query to `ORDER BY at_utc DESC, id DESC`, using the autoincrementing `id` as a deterministic tiebreak. This is a one-line, low-risk change that makes the function actually satisfy its documented contract; I judged fixing it more in the spirit of the brief than leaving a test-order-dependent flaky query in place. Documented in a code comment at the call site as well.

2. **`archive()`'s pre-fetch failure handling.** The brief explicitly left this as a judgment call ("fetching first feels like overkill -- your judgment"). I fetch the row via `get(conn, id).ok()` before archiving, using the name in the summary when available and falling back to `format!("Kunde #{id} archiviert")` / `format!("System #{id} archiviert")` when the fetch fails for any reason. Reasoning: the friendlier, named summary is worth one extra read in the common case, and using `.ok()` (rather than `?`) means even a failure on that fetch can't block the archive itself, consistent with the "never block the primary action" rule that governs the audit-log call itself.

3. **Updated two pre-existing tests in `db/migrations.rs`** (`run_migrations_creates_all_tables_and_records_version`, `running_migrations_twice_is_a_no_op`) that hardcoded a post-migration schema version of `1` and a `schema_migrations` row count of `1`. These weren't mentioned in the brief, but adding migration version 3 to `MIGRATIONS` necessarily changes both values (now 3 and 2 respectively) for any worktree that also applies this branch's migration; leaving them unfixed would have meant `cargo test` failing outright before my own tests ever ran. I also added `"audit_log"` to the table-existence loop in the first test for symmetry with the other tables it already checks. The row-count assertion now reads `MIGRATIONS.len() as i64` instead of a second hardcoded literal, so it won't need another manual fix when the version-2 migration is merged in from the other branch.
