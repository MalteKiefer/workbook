# Report: Dashboard / Startseite (dashboard)

## Summary

Added a new "Dashboard" view that is now the app's default landing screen. It shows two
read only sections aggregated across every active customer:

- **Überfällige Wartungen**: every system that is currently overdue for maintenance
  (per the existing `maintenance::is_overdue` logic), each row showing the system name,
  its customer's name, and how long it has been overdue. Clicking a row jumps to that
  customer's system list.
- **Letzte Einträge**: the 8 most recent journal entries across all customers, each row
  showing the entry title, resolved customer name, and the date it was performed on.
  Clicking a row jumps to that entry's customer's system list, the same honest stopping
  point used for the overdue systems section, since the codebase has no way today to jump
  into the Journal view filtered down to one entry.

A small summary line above both sections shows the active customer count and the total
overdue system count, for example "12 aktive Kunden · 3 Systeme überfällig".

On the backend, this reuses the exact overdue check logic already used by
`list_systems_with_maintenance_status`, just fanned out over every active customer via a
new `list_overdue_systems` command, rather than duplicating or reimplementing any of that
logic.

## Files created / modified

Backend (Rust):
- `src-tauri/src/commands/systems.rs`: added `OverdueSystemDto` and the
  `list_overdue_systems` command (loops over `db::customers::list(&conn, false)`, then
  each customer's systems via `systems::list_by_customer`, computing overdue status with
  `maintenance::is_overdue` exactly as `list_systems_with_maintenance_status` does).
- `src-tauri/src/lib.rs`: registered `commands::systems::list_overdue_systems` in the
  `invoke_handler` list, directly after `list_systems_with_maintenance_status`.

Frontend (React/TypeScript):
- `src/state/appStore.ts`: extended `View` with `"dashboard"`, changed the initial
  `view` to `"dashboard"`, added the `goToDashboard` action.
- `src/App.tsx`: added the "Dashboard" `NavLink` as the first nav item, imported and
  rendered `DashboardView` for `view === "dashboard"`.
- `src/components/DashboardView.tsx` (new): the view itself, containing the summary
  line, the "Überfällige Wartungen" section (fetches `list_overdue_systems`), the
  "Letzte Einträge" section (fetches `list_entries` with every filter field set to null,
  then `list_customers` to resolve customer names, keeping only the first 8 entries
  client side), loading placeholders for each section, and navigation on row click via
  `selectCustomer` plus `goToSystems`.

No other files were touched. No CSS changes were needed since all styling reuses existing
CSS custom properties and the existing `.list-row` class.

## Deviations from the brief (with reasoning)

- **Bug fix in the brief's own `list_overdue_systems` snippet.** The brief's sample code
  builds each `OverdueSystemDto` with `customer_name: customer.name`, which moves
  `customer.name` out of `customer` inside the inner `for system in customer_systems`
  loop. That compiles for a customer with at most one overdue system, but fails with
  compiler error E0382 (use of moved value) as soon as a single customer has two or more
  overdue systems, exactly the case the brief's own suggested test coverage calls out
  (two overdue systems for the same customer both carrying their correct
  `customer_name`). Fixed by cloning: `customer_name: customer.name.clone()`. This is a
  minimal, mechanical fix that preserves the snippet's structure and intent.
- **No new `#[cfg(test)]` module in `commands/systems.rs`.** Per the brief's own
  instruction, I checked first: the file has no existing `#[cfg(test)]` module, and
  command layer tests are not this codebase's convention. Every other command file
  follows the same pattern, a thin wrapper around already tested `db::*` and
  `maintenance::*` functions, with the substantive logic tested at that lower layer, as
  seen in `maintenance.rs`'s and `db::systems.rs`'s own test modules. `list_overdue_systems`
  itself is a thin loop composing three already tested pieces (`db::customers::list`,
  `db::systems::list_by_customer` plus `latest_performed_at`, and `maintenance::is_overdue`),
  so I did not invent a new test module for it, matching the fallback the brief itself
  specifies: manual read through plus a passing build, clippy, and test suite.
- **No additional import needed.** The brief suggested adding either `use crate::db;` or
  extending an existing `use crate::db::...` line so `crate::db::customers::list(...)` has
  "customers in scope." In practice the snippet as given already compiles without any new
  `use` statement, because it calls the fully qualified path
  `crate::db::customers::list(...)` directly, and this file already has precedent for that
  exact style: `list_systems_with_maintenance_status` above it calls
  `crate::maintenance::is_overdue(...)` fully qualified, without importing `maintenance`
  at all. I kept the code exactly as given on this point rather than adding an
  unnecessary `use` line, since the file already has an established convention of using
  fully qualified paths for individual calls into another module.
- **Judgment call, loading indicator on the summary line.** The brief only explicitly
  asks for a "Lade…" placeholder inside the two list sections. I extended the same idea to
  the summary line itself, showing "Lade…" there until both `list_customers` and
  `list_overdue_systems` have resolved, rather than showing "0 aktive Kunden · 0 Systeme
  überfällig" while the real numbers are still loading, which would briefly look like a
  falsely reassuring "nothing to see here" result. This is a small, low risk addition in
  the spirit of the brief's own "no blank gap" instruction.
- **Judgment call, empty state message for "Letzte Einträge".** The brief describes an
  empty state message only for the overdue systems section ("Keine überfälligen
  Wartungen."). I added an analogous "Keine Einträge vorhanden." message for a freshly
  installed instance with zero journal entries, instead of rendering nothing, for the
  same "no blank gap" reasoning and to stay visually consistent with `JournalView.tsx`'s
  own "Keine Einträge gefunden." empty state.
- **`.claude/launch.json`.** I briefly added one to this worktree to try to visually spot
  check the Dashboard in the Browser pane preview tool, but removed it again once it
  turned out to be ineffective (see Verification step 5 above). It is not part of the
  final diff.
