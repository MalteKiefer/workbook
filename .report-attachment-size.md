# Report: attachment-size

## Summary

Implemented the "Anhänge" (attachments) storage summary feature end to end, following the brief precisely. A new backend query, `storage_summary`, reports the distinct-file count and total disk size across all attachments, correctly deduplicating by `sha256` so that a file shared across multiple attachment rows (the same screenshot attached to two different journal entries) is counted once rather than once per row. This is exposed as a new Tauri command, `get_attachment_storage_summary`, and surfaced in a new "Anhänge" section on the General Settings view, alongside a button that runs the existing `cleanup_orphans` command (previously reachable only via the Command Palette). The summary is fetched on mount and re-fetched after every cleanup run so the displayed total never goes stale.

The critical correctness point from the brief, dedup by `sha256` rather than a naive `SUM(size_bytes)`, is implemented exactly as specified (`GROUP BY sha256` in a subquery before counting/summing) and is covered by a dedicated test that would fail under a naive-sum implementation.

## Files created / modified

  - Added `pub fn storage_summary(conn: &Connection) -> Result<AttachmentStorageSummary, AppError>`, using the exact SQL from the brief (`SELECT COUNT(*), COALESCE(SUM(size_bytes), 0) FROM (SELECT sha256, size_bytes FROM attachments GROUP BY sha256)`).

## Deviations from the brief (with reasoning)

- **`formatBytes` was not extracted into a shared utility, and `AttachmentList.tsx`'s `formatSize` was left untouched.** The brief explicitly left this as a judgment call ("your call based on how easy that reuse is without over-engineering a shared-utils extraction for one function"). On inspection, this codebase already has *two* independent, module-private `formatSize` helpers with near-identical bodies (`AttachmentList.tsx` and `EntryDetailModal.tsx`), neither of which is exported, and neither has a GB tier. Extracting a shared `formatBytes`/`formatSize` utility now would mean either (a) creating a new `src/lib/format.ts` module and updating three call sites for a single-purpose, few-line function, which the brief itself warns against, or (b) exporting `AttachmentList.tsx`'s version and importing it into Settings, which would tie an unrelated component's module boundary to the Settings view for no real benefit, and would still need a GB tier added since a store-wide total is far more likely to exceed 1 GB than a single file. Given the existing precedent of duplicating this exact function per-file in this codebase, I judged that adding a third small, self-contained copy (as given verbatim in the brief) in `GeneralSettingsView.tsx` was the more consistent, lower-risk choice, and used the brief's own `formatBytes` implementation as-is.
- **No other deviations.** All Rust struct/function signatures, the SQL query, the command registration point, and the frontend JSX/state/handler shapes were implemented as specified in the brief.
